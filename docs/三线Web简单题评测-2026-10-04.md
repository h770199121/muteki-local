## 2. 三线互补观察

- **每道题至少一条线解出**——三线能力谱互补：Exec/BackupFile 只有 Signal+Bonsai 解出；Include/LoveSQL/Knife Swift 比 Bonsai 强。

## 3. 本轮框架修复（评测前完成，全部真机验证）

1. **RCP bootstrap 三连故障**（Docker Desktop 重启后所有 worker 无法启动，run-20671/20676/20681/20683/20684/20685/20686 逐层定位）：
   - `container_exec.py`：bootstrap token 目录 0700/文件 0600 在 Windows bind mount（gRPC-FUSE）上拒绝一切访问（含容器 root）→ 0755/0644；
   - supervisor（kali）无法 unlink token 时会**故意发空 token Hello**（防重用设计）→ control_dir 0777 使其可消费；
   - 新增 `_verify_bootstrap_token_visible()`：启动 run 容器前用同镜像/同用户/同挂载读回 token + probe unlink，20×0.5s 重试（注意 `--entrypoint bash`——worker 镜像 ENTRYPOINT 是 supervisor，直接传 bash -c 会被当作它的参数，run-20684 的教训）；
   - `docker/worker-ctffix/Dockerfile`：**保持上游 USER root**。zcode-ctf1 首版加了 `USER kali`，导致 supervisor fork worker 时 Go `Credential{}` 的 setgroups 以非 root 身份被拒 → `fork/exec /usr/bin/python3: operation not permitted`（run-20686）。
2. **D07 首次真机触发**：`coordinator_race.py` `_record_worker_resource_limits` 引用 `describe_limits` 但 import 在另一方法局部 → NameError（批次 2 未真机验证的遗留）。已修，`worker_resource_limits` 事件正常发出（unlimited 显式可见）。
3. **receiver 诊断**：`control_receiver.py` Hello 拒绝路径输出 run_id/token 前缀/expected 前缀/live 状态（定位 20683 的决定性证据：token_len=0）。
4. **评测器**：`run_challenge.py` 新增 be1–be7 条目；`solved` 合并 gate 判定（`_gate_solved`）——无官方 flag 的平台题不再漏报解出；21 场重放另存 `results-eval-v2.jsonl`。

## 4. 边界与遗留

- 单轮单样本；20min 预算下 Swift/Bonsai 的失败不等于能力差距定论（方差显著，参照 9.4 节教训需 ≥3 轮统计）。
- 平台提交只对首解计分：Swift/Bonsai 的解出以 gate 判定，未经平台二次确认（gate 有溯源/格式/占位符校验）。
- RCP bootstrap 的 FUSE 行为与 Docker Desktop 版本耦合（重启后权限/可见性语义变化）；`_verify_bootstrap_token_visible` 是通用防线。
- D04 治理器、D07 限额（默认 unlimited）在本轮未触发真实拦截，仅验证了事件链。
- origin push 仍待用户认证（本地领先 fork 8 个提交）。
