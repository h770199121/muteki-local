# 下一步修复方案：writeup 完善（含 web 截图）+ 快速小修

日期：2026-10-04（Asia/Shanghai）。依据：用户指示"制定下一步修复方案，另外需完善 writeup 的功能，如 web 题需包含截图等信息"。

## 0. writeup 现状（代码核实）

- 生成路径：UI"生成复盘"→ HITL `action=writeup` → standby worker 冷启动（dsh，D05-①修复后）→ resume winner 会话（失败降级 fresh+黑板）→ `_RESPOND_WRITEUP_PROMPT`（cli_solver.py:796）→ 纯文本 markdown → 持久化 `sessions/{run_id}/writeup.md`（drivers.py:1904）。
- 两个硬约束决定了截图方案：
  1. prompt 明确"禁止跑命令"（standby 是对话不是新解题）→ worker 自身不能截图；
  2. standby 常在靶机销毁后才触发 → 截图必须发生在**靶机存活期内**，即 run 结束与靶机 teardown 之间的窗口。
- 结论：截图采集方必须是**宿主侧**，且要在 run_challenge 的 teardown 路径自动完成。

## 1. 批次 A：writeup 完善（本轮主项）

### A1 采集器（新 `labs/nyu-ctf/writeup_evidence.py`）

宿主侧脚本，run 结束后、靶机销毁前执行：
1. 从 `sessions/{run}.jsonl` + `workspace/arts/*.txt`（D02 修复后截断输出全量落盘）提取 HTTP 交互：URL、响应 HTML、是否含 flag/成功标记；
2. 筛选关键页面：首页、含 flag 的响应页、登录成功页（响应含 success/flag 类标记）；
3. 用宿主 Playwright 重放 GET（BUUCTF 简单 web 的 flag 页多为 GET 可达；POST 会话态页面为已知限制，记入限制节）逐页截图 → `sessions/{run}/writeup-shots/NN-host.png`；
4. 产出 `sessions/{run}/writeup-evidence.json`：截图清单、对应请求、来源事件 seq、artifacts 指针——供 writeup 引用与事后审计。

### A2 writeup prompt 升级（cli_solver）

`_RESPOND_WRITEUP_PROMPT` 结构扩为五段：漏洞点 / 利用步骤（真实命令+关键响应摘录）/ Flag / **关键截图**（引用 `writeup-shots/*.png`，注明"截图由系统在实例存活期自动采集，若为空说明实例已过期"）/ 证据文件指针（`arts/*.txt`）。仍禁止跑命令——引用文件而非现场采集。

### A3 run 集成（run_challenge.py）

web/remote 场在 `stop_target(ch)` **之前**自动调用 A1（`--skip-shots` 可关）；静态题跳过。这样操作员事后点"生成复盘"时截图已就位。

### A4 验收

Signal 线跑一题（EasySQL）→ 自动截图 ≥2 张（首页+flag 页）→ 点生成复盘 → `writeup.md` 含五段结构与截图引用 → markdown 渲染检查。
