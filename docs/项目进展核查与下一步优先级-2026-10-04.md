项目已经从“补齐工具和修启动故障”推进到“能够完成一轮本地模型 Web 题评测”的阶段。三线 21 场运行的 Gate 结果可由原始事件复核，首批必要上下文与工具回归仍通过。但启动失败治理、部署配置传递和评测统计仍有实际缺口，不能把相关条目标成全部完成。

## 5. 本轮确认的缺口

### 5.1 高优先级：D04 只接入了操作员队列，没有形成全局停止条件

位置：`muteki/swarm/coordinator_dispatch.py:66`、`:126`、`:175`，`muteki/swarm/swarm.py:587`。

`_note_worker_dispatch_failure()` 的唯一生产调用位于 `_apply_worker_cmds()` 的 `_report()`，即操作员 spawn 命令处理。正常 Coordinator 自动派发/回收路径没有统一接入该计数器。

达到上限后，方法设置 `_dispatch_failure_limit_reached=True` 并尝试取消现有 solver、发事件；全库引用检查显示主循环和后续派发入口没有读取该标志来停止调度或生成终态。没有存活 solver 时，甚至没有可取消的对象。

本轮使用真实导入的方法、两个合成 prestart 失败、空 live-solver 注册表，确认结果只有置位与 `worker_dispatch_failure_limit` 事件。该小夹具不等于完整主循环运行，但结合所有引用位置，足以否定“连续失败达上限即停止已经闭环”的结论。

还需处理：同一个已经启动的 live solver 会在每次拒绝时重新清零；启动确认应按新增 receipt 消费，而不是反复拿存活状态当新启动。容量已满也不宜与环境永久不可启动共用致命失败口径。

### 5.2 高优先级：D07 与 D04 的配置没有进入 Compose 控制面

位置：`docker-compose.yml:52`、`muteki/solver/worker_resources.py`、`muteki/swarm/dispatch_failure_governor.py:50`。

执行 `docker compose config --format json` 并只读取 `web-api.environment` 的键，确认以下五项全部缺失：

```text
MUTEKI_WORKER_MEMORY
MUTEKI_WORKER_CPUS
MUTEKI_WORKER_PIDS_LIMIT
MUTEKI_WORKER_RESOURCES_REQUIRED
MUTEKI_MAX_CONSECUTIVE_WORKER_FAILURES
```

Compose 的 `.env` 参与变量替换，不会自动把其中所有字段注入容器。代码从控制面 `os.environ` 读取限额，因此当前部署路径仅修改 `.env` 无法使这些设置生效。`.env.example` 也没有这些配置入口。

此外，批次 2 文档写的是 `MUTEKI_MAX_CONSECUTIVE_FAILURES`，代码实际读取带 `WORKER` 的名称。新旧名称不一致会使用户配置被忽略。

21 场都有 `worker_resource_limits` 事件，证明事件发出路径可用；不能用 unlimited 事件证明配置限额或真实资源拦截已验收。

### 5.3 高优先级：A02 的统一判据仍会被旁路，且多 Flag 判定过宽

位置：`labs/nyu-ctf/run_challenge.py:247`、`:318`、`:421`，`labs/nyu-ctf/eval_verdict.py:181`、`:202`。

两个评测分支都无条件使用 `verdict.solved or gate_solved`，并没有仅在“未知官方 Flag”时采用 Gate 回退。

本轮夹具：真实输出与 Gate 接受的是 `flag{wrong}`，官方值为 `flag{expected}`。`evaluate_attempt()` 返回 false，但最终表达式返回 true。已知答案不匹配仍会被计为解出。这是评测层缺陷，不是生产 Gate 被绕过的证明。

多 Flag 夹具：预期两枚 Flag，只外部确认一枚，`external_verified=any(...)` 仍令 `solved=True`。此外，执行事件目前只要求全局出现过，未关联到被接受候选的具体输出、Worker 与 attempt；调用方没有传入 attempt。应统一已知答案比对、未知答案 Gate 来源、代次和多 Flag 完成条件，输出可定位的接受证据。

### 5.4 高优先级：A01 去除了重复相加，但完整性判断不正确

位置：`labs/nyu-ctf/usage_reduce.py:208`。

当前实现始终优先取 solver 合计，并在 `challenge_rollup <= solver_total` 时判不完整。本轮确定性夹具：

| solver input | 同一运行 challenge input | 返回 input | complete |
|---:|---:|---:|---|
| 100 | 100 | 100 | false |
| 100 | 150 | 100 | true |
| 100 | 50 | 100 | false |

前两行分别把一致账本判为不完整、把明显遗漏 50 的账本判为完整。仅把比较符号反过来也不足以解决“旧 rollup + 新 solver 用量”的混合时间点问题；需要事件顺序、覆盖范围及 Coordinator 调用身份。

真实 Signal 三场存在 challenge 级记录与后续 solver 记录，当前总量与原因文本不能充分解释覆盖关系。历史 run-20670 仍可重放为 solver input 1,563,948 / output 52,737，但这是 solver 台账口径，不是确定的完整运行总量。

### 5.5 中优先级：D08 的端点身份、定价和记账尚未统一

位置：`muteki/core/cost.py:81`、`:184`、`:262`，`muteki/solver/cli_solver.py:6900`。

`price_status()` 在 model 字符串中寻找 localhost 等标记，没有读取实际 endpoint。真实本地 Worker 因此仍记为 `qwen3.8-27b / unpriced`；三场 Signal 中还存在 `deepseek-v4-flash / exact` 的 challenge 级调用。不能据此断言调用了云端，但能确认身份与成本口径仍不完整。

真实导入夹具进一步确认：给 `localhost-model` 配置非零价目时，`price_usage()` 报 `local_zero_api_cost / 0 USD`，而 `record()` 实际记入 `1 USD`。后者仍直接拿 price 调用 Ledger.add，没有统一使用前者裁定的金额。

### 5.6 中优先级：RCP 修复保留了凭据片段日志和部署假设

位置：`muteki/solver/control_receiver.py:499`，`muteki/solver/container_exec.py:682`、`:788`。

### 5.7 中优先级：D02/D06 仍缺运行级的交付证据

位置：`muteki/solver/worker_skills.py:92`，现有控制上下文 manifest 位于 cli_solver/coordinator_race。

## 7. 推荐的下一批工作与验收

### 第一批：让保护和结果可信

实施范围：第 5.1–5.6 节。重点是修已有路径，不增加新调度架构。

验收应覆盖：

- 自动 Worker 启动失败确实被计数；达到配置上限后不再派发，产生清晰终态；真实新增启动 receipt 清零；普通运行失败不混入。
- Compose 注入的五项配置可观测，实际容器的 memory/CPU/PID 与请求一致；配置非法、不设限、超限和取消均有可解释结果。
- 已知 Flag 不匹配必定失败；未知官方值仍可用来源明确的 Gate 结果；旧代次、只含文本、多 Flag 未齐不能误报。
- solver/Coordinator 用量在累计事件、缺事件与恢复场景下可解释，未覆盖部分明确标未知；不能靠一个 max/sum 或翻转比较符号掩盖。
- 成本分类、实际记账与预算消费一致；运行模型和端点身份可追溯；RCP 日志不含 token 内容。

新增测试应调用实际消费路径，而不是只断言源码中存在函数名。本轮 143 项通过与上述缺陷同时存在，已经说明仅靠现有测试不足以验收这一批。

### 第二批：建立可复验基线并补交付记录
