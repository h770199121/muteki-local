# muteki-local 的 CTF 能力增强调研

调研日期：2026-10-03（Asia/Shanghai）。范围：指定的四个仓库、其中与 CTF 直接相关的框架和工具，以及本机 muteki-local、独立 dsh 的配置和实现。

## 1. 建议

**保留 muteki 的任务管理、容器、证据和 Flag 校验，优先改进它所调用的单个 dsh Worker。首选引入经过筛选的 ctf-skills 技术资料，并把容易出错的操作封装成可验证工具。暂不整体迁移到 dsh + 全量 KaliClaw。**

原因是：当前系统已经包含 dsh + KaliClaw 精选知识库；重复安装并不能解决“技能没有被读取、证据没有被正确解释、已成功的中间步骤没有接续”这些实际失败。直接使用 dsh 可能减少调度和提示传递损耗，值得作为对照组，但没有同模型、同环境实验支持它必然更强。

优先顺序：

1. 修知识检索和技能送达；把技能读取与实际应用做成可观测事件。
2. 封装 HTTP 会话、响应对比、文件解码、PCAP 提取、二进制初筛等确定性操作。
3. 接入 ctf-skills 的精选方法、crypto-attacks / RsaCtfTool 等现成算法实现。
4. 比较精简 muteki 调度与直接 dsh，保留相同运行时和知识输入。
5. 允许云端时，增加按需强模型难点审查；必须完全离线时，再比较量化精度、专项模型和离线蒸馏。

这里的排序是工程判断，不是已经测得的解题率排名。

### 2.2 已存在的证据

本地报告在 7 道早期题上记录三条模型线分别为 2/7、3/7、3/7。这些是小样本、旧模型配置的结果，不能推算当前 Signal 双卡配置的整体成功率。

`run-20282` 有可复核的正面案例：Include 题在加入经验补丁后，185.4 秒、8 次工具调用完成。原始事件含获取编码源码、解码输出、提交 Flag 和 `run.finished.solved=true`。本轮抽查了这些事件，没有重新连接远程题目。

这说明经验可以补上具体操作缺口；**它是已见题的辅助回归成功，不是泛化提升的充分证据**。旧文档所说“稳定解出”应保守理解为一次成功运行。已向 KB 加入具体解法的 no-pass-needed / Include，后续只能作为回归题或单独的辅助条件评测。

`eval_nyu/_reports/FINAL_eval_report.md` 的“200/200”属于 Opus / GPT / Cursor 等异构云模型组合的历史报告。本轮未独立审计全部轨迹，更不能把这一结果归给本地 27B 模型。

### 2.3 本轮直接复现的检索问题

在内存 SQLite 中用现有 `kbsearch.py` 的分块和索引函数建索引，共 4,755 块；没有写入或更新磁盘索引。

| 查询 | 实际处理与命中 |
|---|---|
| `登录 过滤 绕过` | 正则处理后为空，无法检索 |
| `SQL 注入 过滤` | 只剩 `SQL`，中文约束全部丢失；前三项是 SSRF/MySQL、二次 SQLi、数据库密码散列 |
| `login filter bypass` | 能找到目标登录过滤章节，但排在两个 command-injection/LDAP 章节之后 |
| `cookie session` | 前三项偏向 LFI session 文件和 XSS cookie stealing，而非基础会话保持 |

代码原因是 `kbsearch.py:90` 只保留 `[A-Za-z0-9_]{2,}`，检索范围也仅为自身 `kb/*.md`。增加其他仓库文件不会自动进入这个索引。

应先补中英术语映射、题型/工具过滤、标题和标签加权、无命中回退，以及一组人工标注的“症状→正确章节”检索回归题。对于较小知识库，先把现有 FTS 做好，再评估是否需要向量检索和重排。

### 2.4 工程问题仍需与模型问题分开

历史记录包括提示被 planner 稀释、standby hint 失败和中断后恢复失败。当前源码 `apps/web/drivers.py:1492` 仍能看到 `winner.get("engine") or "claude"` 回退。应测试无 winner、当前只启用 dsh 时的完整路径；本轮静态发现不能替代运行复现，也不证明历史其他问题仍全部存在。

`stage_extra_skills()` 和 AGENTS 指针均保留已存在文件。更新源技能后，复用的 Worker 目录可能继续使用旧副本。集成时应记录技能版本/内容指纹，并验证实际 Worker 加载的是哪个版本。

### 3.1 ctf-skills：最适合直接补充技术方法

目录树实际有 11 个 `SKILL.md`：9 个类别技能，以及 `solve-challenge`、`ctf-writeup`。覆盖 Web、Pwn、Crypto、Reverse、Forensics、Misc 等比赛常见题型，附有具体方法、代码片段和可运行脚本。

相对当前 KaliClaw 蒸馏库，值得优先吸收：

- Crypto 的攻击前提、RSA/ECC/格/PRNG 专项索引，以及外部算法实现入口。
- Reverse 的 Ghidra headless、Unicorn、动态分析、字节码和自定义 VM 方法。
- Web 的请求基线、Session、输入转换差异和认证状态保持。
- Forensics/Misc 的 PCAP 还原、文件雕刻、编码链和 jail 分类。
- Pwn 的参数化模板，配合真实二进制测得的偏移、保护和地址使用。

需要适配的地方：

1. **技能并不都短。** 当前 `ctf-crypto/SKILL.md` 约 42KB，forensics 约 37KB。把完整分类文档塞入每次请求，会占用弱模型的注意力。更合适的做法是短路由卡 + 精确章节检索。
2. `allowed-tools`、斜杠命令、`Task` 和 `Skill` 的名字有客户端约定，必须映射到实际 dsh 工具。安装文件不等于这些能力已经可调用。
3. `solve-challenge` 是另一层调度说明。保留它的分诊逻辑即可，不必让它与 muteki Coordinator 争夺任务控制。
4. 跨技能引用、`../scripts/` 和 PayloadsAllTheThings 路径必须保持可解析。只复制某个 SKILL.md 会丢失依赖。
5. 本轮抽查的 `tests/test_pwn_scripts.py` 明确是 mock pwntools，注释写明没有真实网络或二进制；这些测试不是端到端解题率。
6. 文档代码仍需工程审查。例如 `ctf-web/python-requests.md` 的 Session 示例写着“uncomment to route”，实际代理赋值已生效，直接复制到没有 Burp 的容器会连接失败。

来源：[分诊入口](https://github.com/ljagiello/ctf-skills/blob/c332c7be1b27cb64639a20124ac55ba916adef92/solve-challenge/SKILL.md)、[Crypto](https://github.com/ljagiello/ctf-skills/blob/c332c7be1b27cb64639a20124ac55ba916adef92/ctf-crypto/SKILL.md)、[Reverse 工具](https://github.com/ljagiello/ctf-skills/blob/c332c7be1b27cb64639a20124ac55ba916adef92/ctf-reverse/tools.md)、[Pwn 测试](https://github.com/ljagiello/ctf-skills/blob/c332c7be1b27cb64639a20124ac55ba916adef92/tests/test_pwn_scripts.py)、[HTTP 示例](https://github.com/ljagiello/ctf-skills/blob/c332c7be1b27cb64639a20124ac55ba916adef92/ctf-web/python-requests.md)。

### 3.2 reverse-skill：借鉴路由和工具契约

它不是只有逆向文章，还包含结构化路由、工具探测、案例目录、证据记录和平台适配。其 `CTF-Sandbox-Orchestrator` 在目录树中有 42 个技能文件，倾向“先证明最小路径，再按证据下钻”。

适合移植的思想是：以文件类型、服务行为、现有证据和工具能力决定下一步；每次只交付当前需要的专项说明；对工具缺失与方法失败作区分。

不宜整体复制 RULES / AGENTS / 总控说明：它们与 muteki 已有黑板、scope、调度、审查和结果契约部分重复。其“默认把目标视为沙盒内部资产”的工作假设也不应替代 muteki 显式提供的题目范围。

README 的路由用例数存在不同历史口径；本轮实际解析 `skills/tests/routing-benchmark.json` 得到 **178 条 hint→expected route 用例**。这是路由回归测试，不是 178 道 CTF 解题成绩。

许可证也需分开：主仓库 MIT，内含 CTF-Sandbox-Orchestrator 标注 GPLv3；不能将整个目录统一当成 MIT 材料。

来源：[路由用例](https://github.com/zhaoxuya520/reverse-skill/blob/cab634bd855fc287f6e420c1f36fd1a6b9245960/skills/tests/routing-benchmark.json)、[CTF 入口](https://github.com/zhaoxuya520/reverse-skill/blob/cab634bd855fc287f6e420c1f36fd1a6b9245960/CTF-Sandbox-Orchestrator/ctf-sandbox-orchestrator/SKILL.md)。

### 3.3 Anthropic-Cybersecurity-Skills：适合补缺

目录树有 818 个技能，README 列出 34 个领域，大量内容面向企业安全、检测、云、身份与合规。对于混合实战靶场有用，但“更多安全领域”不等于对传统 CTF 的贡献更大。

建议按需要选择二进制初筛、Ghidra、Volatility、网络取证、隐写、SQLi 等技能。抽查的 `performing-binary-exploitation-analysis/scripts/agent.py` 能输出保护属性、危险函数候选和 ROP gadget，这是有价值的工具化方向；它不会自动证明漏洞可达，也不是完整 Pwn solver。

例如仅凭 ELF 中出现 `gets` 就给出“guaranteed buffer overflow”的描述过强；该信息应进入待验证候选，而非 muteki 的 verified fact。模板中的示例地址、偏移也必须由当前题目证据替换。

来源：[二进制分析技能](https://github.com/mukul975/Anthropic-Cybersecurity-Skills/blob/54a798831d2266a3ca61ce68a7acb80b81160d57/skills/performing-binary-exploitation-analysis/SKILL.md)、[分析脚本](https://github.com/mukul975/Anthropic-Cybersecurity-Skills/blob/54a798831d2266a3ca61ce68a7acb80b81160d57/skills/performing-binary-exploitation-analysis/scripts/agent.py)。

| [verialabs/ctf-agent](https://github.com/verialabs/ctf-agent) | 比赛调度、工具镜像、跨 solver 线索共享 | 52/52 是项目自报比赛成绩，模型表为 Opus/GPT 等；不能外推到本地 27B |
| [tinyctfer](https://github.com/chainreactors/tinyctfer) | 精简核心、提示变化、模型/Agent 切换经验 | 依赖 Claude Code 与 Anthropic 兼容 API；作者说明比赛完整调度未全部包含，不能把名次移植成此核心代码的本地成绩 |

| [P4nda0s/reverse-skills](https://github.com/P4nda0s/reverse-skills) | 为 IDA-NO-MCP 导出结果设计的符号/结构分析、Frida/Unicorn 技能 | 已有 IDA 工作流时有价值；当前也可用 Ghidra headless 先导出，再精确检索函数，无需为了 MCP 先换平台 |

更直接的收益常来自被这些技能引用的算法与工具：

- [jvdsn/crypto-attacks](https://github.com/jvdsn/crypto-attacks)：Sage/Python 密码分析实现与测试。让模型识别攻击前提并提供参数，比临时编写整个格攻击算法可靠；格维度、参数和攻击适用条件仍需检查。
- [RsaCtfTool](https://github.com/RsaCtfTool/RsaCtfTool)：常见弱 RSA 条件的自动检查和攻击。适合作为受预算约束的候选工具；完全离线模式要排除 FactorDB 等联网路线。
- [PayloadsAllTheThings](https://github.com/swisskyrepo/PayloadsAllTheThings)：ctf-skills 明确作为按需外部 payload 来源。应按已验证的注入类型检索，不能把整库变成默认请求列表。
- Ghidra、GDB/pwndbg、angr、Unicorn、Z3、SageMath、tshark、Volatility：用结构化参数和有限输出封装它们，减少模型拼错命令、抄错偏移和误读长输出的机会。

当前完整版 Worker Dockerfile 已声明安装 Ghidra、SageMath、angr、Z3、tshark 等。先核对实际使用镜像的版本与可调用性，避免把“缺乏正确调用”误诊成“缺少整个 Kali 环境”。本轮没有启动 Worker 验证这些依赖。

## 5. dsh + KaliClaw 是否优于当前 muteki

### 5.1 应按层比较

| 层次 | 当前 muteki-local | 直接 dsh + KaliClaw |
|---|---|---|
| 推理能力 | 由配置的本地模型决定 | 若仍是同一模型，基础能力相同 |
| Agent 执行 | dsh SDK 与事件桥接 | dsh 的独立 profile；需要固定真实运行时版本 |
| 安全知识 | KaliClaw 精选 24 域及本地补丁 | 可装精选或全部 139 域；全量收益未证实 |
| 任务控制 | Coordinator、黑板、Flag gate、预算、UI、人工指令 | 可以简化；需要补齐所需的判定、状态和评测能力 |
| 可能收益 | 保留证据与控制设施，能接更多执行器 | 少一层规划、转述与重派，适合单题交互 |
| 主要不确定性 | 弱 planner、提示损失、控制路径错误 | 长对话循环、技能调用、最终判定和跨尝试状态仍需解决 |

DeepSeek 官方将 dsh 定义为插件化 harness；其[架构说明](https://github.com/deepseek-ai/deepseek-harness/blob/main/docs/architecture.md)显示 SDK 和独立入口可共享基础能力，工具、模型、压缩、指令和 profile 可配置。它不是另一套自动增强模型知识的权重。

因此可以先在 muteki 中改进 dsh 配置/桥接，而不必丢掉整个外层系统。只有同条件测试确认额外调度持续拖累后，才有依据让本地单题默认走更精简路径。

### 5.2 KaliClaw 的“验证”应如何理解

[KaliClaw README](https://github.com/brucesongs/kali-claw)当前标注 v0.3.5、139 技能，是从 OpenClaw 工作流发展而来的可移植知识包。它的心跳、记忆和自更新，不意味着本地模型权重自动变强。

[v0.3.5 验证说明](https://github.com/brucesongs/kali-claw/blob/main/RELEASE-v0.3.5.md)主要衡量内容完整性、命令语法、链接和文档可靠性：139 技能覆盖、bash 语法错误修正、skill-lint 等。**这不能证明 139 个领域都有端到端 CTF 解题能力。**

仓库保留的[旧版 CyberGym 全量尝试报告](https://github.com/brucesongs/kali-claw/blob/main/docs/legacy-reports/RELEASE-v0.1.47.1-final-report.md)记录中途结束，1,087 实例仅 1 个 PASS，并涉及大量基础设施和命令参数问题。不能把该 0.09% 当成现版 KaliClaw 的 CTF 解题率；同样，也不能用小样本旧版高分或当前文档评分证明它优于 muteki。

## 6. 本地模型较弱时的具体改进

### 6.1 让关键操作少依赖生成能力

以“短决策卡 + 参数化工具 + 可验证输出”替代不断增长的系统提示。

| 工具方向 | 固定承担的操作 | 交还模型的决策 |
|---|---|---|
| HTTP 会话助手 | 保存 cookie、跟踪跳转、请求/响应留档、输入回显差异、状态变更 | 哪个差异支持哪个假设，下一次只改变什么 |
| 解码/提取助手 | 区分 HTML 包装与编码片段、验证解码、识别文件类型、保存中间产物 | 哪条编码/容器假设符合题目证据 |
| PCAP 助手 | 协议统计、流重组、文件导出、索引产物 | 哪个流或协议值得继续调查 |
| 二进制助手 | 架构/保护/导入、反编译函数、交叉引用、崩溃证据 | 漏洞原语、约束与下一步验证 |
| Crypto 助手 | 参数解析、攻击前提检查、调用已测试算法、核对恢复结果 | 选择符合前提的攻击，而非凭名称盲试 |

每个工具输出至少保留：原始产物路径、输入参数、关键观测、执行错误、适用前提是否满足。不要让工具直接把“可疑”写成“已验证”。

HTTP Session 工具直接对应 no-pass-needed 已登录成功却不会正确复用 cookie 的失败。解码工具直接对应 Include 响应污染导致放弃的失败。把这些步骤变成可靠程序，比再写一段“务必注意 cookie/base64”的文字更有针对性。

### 6.2 控制上下文与停滞

- 区分原始日志与模型当前视图。完整日志落盘；模型只看当前假设、关键证据、已排除路径和产物索引，必要时回查原文。
- 对等价请求、相同输出和重复错误做程序检测。触发一次有限的重审或换路线，不能只是让同一个模型无限“再想想”。
- 把关键状态表示为明确检查点，例如“认证响应变化已确认 / 带同一会话访问目标尚未确认”。不要只靠自然语言总结“登录似乎成功”。
- 外部 planner 只有在提供了新的、有证据支撑的方向时才算收益。现有单 Worker 配置已避免部分并发浪费；下一步应测规划质量，不是继续增加角色数。
- 小模型做抽取/去重/格式校验可以试验，但不应宣称更小 planner 一定能“根治”27B 的规划问题。能确定性实现的检查优先用程序。

### 6.3 模型、量化与算力

当前脚本仍指向 IQ3_XXS 级量化。双卡容量增加后，可以把同底座更高精度量化列为独立实验变量；应同时报告解题质量、prefill/decode、上下文占用和墙钟时间，不能凭位数预言收益。

当前启动参数的大上下文窗口也不等于模型能可靠利用全部历史。应做有效上下文长度与摘要策略的对照，观察证据遗漏和重复率。

本机已有 vLLM/WSL2 双卡初始化失败记录。更换推理栈或系统可能改善吞吐、容量与兼容性，但本轮没有证据表明它直接解决 CTF 推理缺口。先修检索、工具和控制路径更容易衡量收益。

### 6.4 完全离线与可少量联网的两条路线

**完全离线：** 冻结经审核的技术资料和工具；先完善执行封装，再考虑模型专项训练。[Cyber-Zero](https://github.com/amazon-science/Cyber-Zero)报告用模拟轨迹训练后，在指定旧基线/评测中最多提升 13.1 个百分点，并提出 Cyber-Zero-32B、EnIGMA+；这不是对当前 Signal 的优势证明。其生成轨迹包含模拟执行结果，若用于自己的经验库，应通过真实执行验证关键步骤。

[HackSynth-GRPO](https://github.com/aielte-research/HackSynth-GRPO)提供 Random-Crypto、工具调用评测和 GRPO 训练；适合研究专项参数化任务。它的 Crypto 改进不能直接外推到 Web/Pwn。训练数据必须与留出题及其变体分离，不能拿 NYU test 题的解法训练后又在同一 test 集报告泛化。

**允许少量云端：** 本地模型负责执行、采集和常规路线；明确停滞时把最小证据包交给强模型，请其提出下一项可证伪实验，回到本地执行并验证。相比让强模型持续承担全部工具循环，这更容易控制费用。这里仅列方案，未调用云模型处理本地题目或发送题目文件。

## 7. 应怎样做公平对照

先固定模型、量化、推理参数、实际 dsh runtime、工具镜像、题目附件、网络条件和预算，再比较外层调度与知识增强：

| 实验臂 | 调度 | 知识与工具 |
|---|---|---|
| A | 当前 muteki | 当前 KaliClaw 精选库 |
| B | 直接 dsh | 与 A 相同；使用共同的外部评分与证据采集 |
| C | muteki | 精选 ctf-skills + 检索修复 + 操作封装 |
| D | 直接 dsh | 与 C 相同 |

A/B 分离调度影响，A/C 衡量增强组合在 muteki 中的收益，C/D 判断增强后是否还应保留当前调度。若要归因到单一改动，再拆开检索修复、技能内容和操作封装逐项消融。

“升级 npm dsh + 换知识库 + 去掉 Coordinator”可以作整套产品体验比较，但不能解释究竟哪项造成提升。

评测条件：

- 保留项目已有 web 30 分钟、静态题 15 分钟口径作为可选基准；如改预算则另开实验组，并报告实际墙钟与超时收尾开销。
- 覆盖 Web、Crypto、Reverse、Pwn、Forensics、Misc；同题多次独立尝试，重置目标、会话、工作目录和跨运行记忆。
- 将已读解法/已写入 KB 的题、真正留出题、联网辅助题分开；跨题经验也要冻结到同一版本。
- 统计 pass@1、固定总预算内的成功率、首次有效证据时间、重复动作、空转时间、技能加载及应用、失败分类。
- 区分模型错误、调用/协议错误、工具缺失、目标故障和调度故障。不能把基础设施失败全部解释成模型不行。
- 当前 token 统计包含 cache_read 汇总；重复计入缓存的输入 token 不等价于实际重新计算量或费用，墙钟、生成 token 和缓存量应分列。
- 用题目验证器或评分端不可见的 ground truth 判定成功。保留 gate 的真实执行溯源；仅出现合法格式字符串不足以证明题目解决。

没有经过这套对照前，结论应是“推荐试验/集成”，不是“已经提升了多少”。

## 8. 建议实施边界

| 优先级 | 具体范围 | 验证证据 |
|---|---|---|
| 第一批 | `kbsearch.py`：语言/召回/排序；技能内容指纹；确认挂载、复制和实际读取 | 人工标注查询命中；Worker 事件可定位加载的章节与版本 |
| 第一批 | 单独增加 HTTP 会话与解码工具；现有 gate 保持独立 | 已知失败的小型夹具可复现；未见同型题多轮试验 |
| 第二批 | 建精选 CTF 资料包；仅下钻相关章节；保留相对资源路径和许可 | 文件/链接/依赖检查；相同预算下与原库对照 |
| 第二批 | 针对 dsh 的 runtime/profile 兼容核查；hint 与 resume 定向复现 | 同一运行时下控制消息实际到达，恢复后继续产生真实工具输出 |
| 后续 | 外层调度消融、更高精度模型、按需强模型审查、专项训练 | 留出题分组结果和完整轨迹 |

不建议一次接入多个总控、全量 818 个技能、全量 MCP 工具，或重写整个 muteki。应把协议留在框架、把方法留在技能、把可确定步骤放进代码、把历史经验留在有来源的知识库。
