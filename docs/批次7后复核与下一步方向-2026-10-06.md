## 4. 必须收尾的问题

### 4.1 最高优先：部署仍停留在旧行为

对当前 Web 容器直接读取文件并与工作区比较：

| 文件/行为 | 工作区 | 运行容器 |
|---|---|---|
| `apps/web/server.py` | retention 默认关闭 | retention 默认开启 |
| `apps/web/drivers.py` | 清单输入使用 `model_dump_json()` 归一化 | 没有该入口修复；已有最终正文 `final_text=body` |
| `muteki/core/llm.py` | 缺模型地址报错 | 仍有 `https://api.deepseek.com/v1` 默认回退 |
| `muteki/solver/writeup_evidence.py` | 有 `_etype()` | 无 `_etype()` |
| `labs/nyu-ctf/eval_verdict.py` | verdict 版本 4 | 容器可见文件字节相同；不能据单文件相同推断整个镜像一致 |

容器环境及其 `/app/.env` 均未设置 retention 覆盖项，因此旧的默认自动归档/删除策略仍未被新“默认保留”要求替代。本次没有声称已经发生实际删除，但不能仅因 Git 源码改成 0 就认定线上行为已经改变。

建议先核对有效保留配置，再用本地已验证代码构建并对齐部署，确认容器内关键文件和行为。不要使用仍指向官方上游的默认更新器来替代本地定制版。部署前后保留运行资料，按已确认的空闲安装/回滚策略处理。本次审计没有重启、替换或停止现有服务。

### 4.2 新增三场 T4 记录均未进入求解

`run-23541`、`run-23545`、`run-23549` 的原始事件各只有 2 条，没有 Worker started；终态均为：

```text
reason = preflight_failed
failure_code = profile_unhealthy
profile_failures.layer = auth
profile_failures.code = preflight_auth_failed
```

因此它们是启动/认证预检失败记录，不能作为模型解题失败或性能对照。当前宿主 `/health` 的 400 只说明该次健康请求未成功，尚不足以定位是协议、代理、认证还是健康路由问题。

下一步应从有效 Profile、18221 服务协议和容器内认证请求入手，确认端点可达与认证通过后，再做一场本地可控功能验收。避免在相同预检失败下重复提交求解任务。本轮保留 T4 映射、现有模型配置和新增结果，没有切换模型或修改凭据。
