## 4. 本次确认的剩余缺口

### 4.1 评测证据：最新真实成功场仍被漏判，代次约束没有接到调用方

这是批次 5 最适合先修的确定性问题。

**真实样本：** `run-23529` 在 [原始结果](../labs/nyu-ctf/results.jsonl) 中为 `gate_solved=true`、`solved=false`、`gate_accepted=false`。本次用当前评测器重放仍得到同样的证据缺口，不只是旧 4 场历史数据的问题。

可追溯来源已经在磁盘上：

- [原始事件](../data/sessions/run-23529.jsonl) seq 122，Worker `cli-dsh-2`、generation 1，`result.artifact_id=c424c2e0397f`。
- [对应原始输出](../data/sessions/run-23529/workspace/arts/c424c2e0397f.txt) 确实含该运行接受的 Flag；SHA-256 为 `ff389c4c5b2520c62f42c05162c386c92c4164005a39b5ced5e736ba06ccd8f3`。
- 同目录另一份 `f3c28522d884.txt` 也含 Flag，但本次找不到引用它的事件。这正说明不能把“目录内任意文件命中”作为同等强度的接受来源。

`run-22883` 可作为嵌套 artifact_id 兼容样本，但它在当前评测器下已经能由其他事件输出判为成功，不能单独作为“新增回查修好了漏判”的验收样本。

**代次与时序：** `run_challenge.py` 335、450 行及 `replay_eval.py` 121 行调用 `evaluate_attempt()` 时均未传 `attempt`。`env_binding.attempt=1` 不会自动成为评测过滤条件。评测器只保存输出 seq / text / generation，没有绑定 run、Worker、tool call，也没有核对输出与接受的时间关系；显式传入代次后，缺失 generation 的事件仍被宽松接纳。

本次执行当前模块的内存夹具，结果如下：

| 输入 | 实际判定 | 应补的契约 |
|---|---|---|
| 第 1 代工具输出，第 2 代成功终态，按当前调用方式不传 attempt | `solved=true`、`attempt_matched=true` | 调用方传真实代次，禁止无依据串代 |
| 成功终态之后才出现包含 Flag 的输出 | `solved=true` | 接受来源必须能关联到该次判定；异步乱序应依靠来源 ID，而不是任意字符串命中 |
| `attempt=2`，输出无 generation，接受事件为第 2 代 | `solved=true` | 历史兼容路径保留不确定性，不能声称严格匹配 |

这些是评测层的缺陷，不等于生产 Flag gate 被绕过。

修复建议：从接受记录回查同 run / generation 内的具体输出事件，再读取该事件引用的 artifact。兼容顶层与 `result.artifact_id` 两种记录；限定工作区内可读路径并记录 SHA-256、event seq、Worker、generation 和缺失原因。无关联文件只能成为候选线索。新旧结果应有独立 verdict 版本，重放输出另存，不覆盖原始记录。

### 4.2 writeup：磁盘报告与界面收到的报告不一致

[drivers.py](../apps/web/drivers.py) 1919 行将附录加入 `body`，1923 行保存完整报告；但 1936 行 `followup.completed.payload.text` 仍发送原始 `out.reply`。

[events.ts](../apps/web/ui/lib/events.ts) 2737 行开始的完成事件处理只消费 `p.text`；本次搜索未找到 UI 调用 `GET /api/runs/{run_id}/writeup` 获取完整报告。

真实样本 `run-23529`：

| 载体 | 本次结果 |
|---|---|
| [workspace/writeup.md](../data/sessions/run-23529/workspace/writeup.md) | 有“关键截图与证据”附录，含 2 个图片引用 |
| 原始事件 seq 152 `followup.completed.text` | 1678 字符，无附录、无图片引用 |

因此当前证据可以证明文件生成，但不能证明普通界面显示了确定性附录。基础图片渲染器存在也不能补上缺失的数据。

另有两个实际接线问题：

- Web 的 `POST writeup-evidence` 每次重新创建 `screenshots=[]` 的 manifest 并覆盖旧文件，可能抹去宿主已采集的截图引用；应保留有效采集记录或拆分可合并的产物。
- 普通 UI 的“生成复盘”只发送 writeup 指令；本次未找到自动调用清单刷新接口或宿主截图采集器的链路。评测脚本的采集成功不能直接覆盖普通 Web 使用场景。

建议先让最终保存正文与 UI 展示读取同一版本，再补普通 Web 入口的证据准备。验收必须覆盖生成、刷新、切换运行后重新打开，以及没有截图和部分采集失败的状态；不以 Markdown 文件含图片语法代替浏览器验收。

### 4.3 重启恢复：已有历史回填和“继续做题”，缺的是持久化中断语义

批次 5 说“没有 run 级/swarm epoch 自动恢复”成立，但“新增继续解题按钮并走 standby/resume”的方案不符合现有代码职责。

- [run_manager.py](../apps/web/run_manager.py) `_recover_interrupted_followups()` 只对 ask/writeup 补失败事件。
- `_rehydrate()` 已为历史 run 重建句柄，并把 Protocol 1 的已启动运行在内存中标记 finished；它没有为进程中断补写对应 run 终态。Protocol 2 有不同的权威状态约束，不能一起用扫描规则硬写终态。
- `resolve()` / `_resolve_launching()` 已存在；“继续做题”按钮也已存在。该路径会重开 generation、重启完整 Coordinator 并复用 workspace / shared graph；standby 是另一条追问/报告路径。
- `run-23532` 的归档仍只有 12 个事件，无 `run.finished`，符合历史重启未闭合的记录。本次没有再次重启服务。

推荐最小路线 A：对**最新未闭合 generation**进行幂等中断对账，持久化原因并统一后端摘要、SSE 重放和 UI 状态；继续操作复用既有 `resolve()`，保持手动触发。要处理 `run.reopened`、worker scope、旧 generation 已结束、新 generation 中断等情况，不能仅按“全文件有 started 而无 finished”判断。

验收还应包括连续两次重启不重复补终态、无 winner 的继续、旧 Worker / 迟到事件隔离、运行所有权和取消清理。自动续跑仍是待决定的产品行为，本次未将其视为已经批准。

### 4.4 截图：请求配对和重放语义优先于重试次数

[writeup_evidence.py](../muteki/solver/writeup_evidence.py) 采用跨所有 Worker 的全局 FIFO 配对工具事件。本次构造 A/B 两 Worker 先后发请求、B/A 顺序返回的夹具，得到 `a.test → response B`、`b.test → response A`，证明 URL 和响应可能错配。单 Worker 默认减小了触发范围，但并行工具、其他配置和历史交错事件仍需正确关联。

宿主采集器说明宣称 POST / session-state 会标记不可重放，实际代码没有解析请求方法或会话状态。内存夹具中的 `curl -X POST ... -d ...` 仍进入 `key_pages`，随后会被统一 GET 重放。保存一张 GET 页面图不等于保存原始成功请求。

还需修订以下验收描述：

- `run-23529` 两张已存截图对应 seq 18、35，manifest 均标为 `http page`；其余两 URL 失败。该资料不能证明“首页 + 成功页至少 2 张”的既定条件已经满足。
- 失败 notes 只有 `npx playwright failed`，代码还把错误截到 500 字符。现有证据不足以确定根因是 npx 并发/缓存竞态；应检查退出码、调用参数和完整诊断，尤其带查询串的 Windows 命令传参。
- 每页最多两次 `timeout_s + 40` 等待，但外层采集进程总超时为 140s，manifest 在全部采集后才保存。整体超时可能丢失已完成页的清单；总截止时间、阶段落盘和子进程清理需要一致。

建议按 `(run, generation, Worker, tool call)` 关联 HTTP 交互，明确 method / 会话依赖 / replay 状态；先保存真实响应，再做可解释的浏览器重放。随后定位查询串失败，并考虑复用一个浏览器进程，而不是先增加重试或更换依赖。

### 4.5 D04：实现已接线，仍缺主循环级退出验收

历史 `run-23531` 只有准备和失败终态，属于坏镜像预检失败。它不能证明“预检通过、实际启动连续失败、达到阈值、停止再派发、取消存活 Worker”这条主循环路径。

本次真实 mixin 测试通过，`coordinator_loop.py` 666 行也有达到失败上限后取消并退出的代码。下一步应构造预检正常而执行器 pre-start 失败的定向夹具，验证 stop_reason、计数重置、取消以及只产生一个当前 generation 终态。继续沿用现有配置来源，不从此次观察推导新阈值。
