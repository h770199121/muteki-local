## 1. D07 — Worker 资源上限 ✅

### 缺口确认

`container_exec.py:724-729` 已是条件式追加：

```python
if memory:      run_cmd += ["--memory", str(memory)]
if cpus:        run_cmd += ["--cpus", str(cpus)]
if pids_limit and int(pids_limit) > 0: run_cmd += ["--pids-limit", str(pids_limit)]
```

但唯一生产调用点 `coordinator_race.py:1808` **三项全未传**（`drivers.py` 与 `cli_driver.py` 只是复用已有 handle，不单独建容器）。故 `--memory/--cpus/--pids-limit` 从未出现在实际 `docker run` 中。

### 改动

| 文件 | 内容 |
|---|---|
| `muteki/solver/worker_resources.py` | **新增**。集中解析有效限额 |
| `muteki/swarm/coordinator_race.py` | `resolve_limits()` + `**as_kwargs()` 接入；新增 `_record_worker_resource_limits()` / `_emit_worker_resource_limits()` |
| `muteki/swarm/swarm.py` | 初始化 `_worker_resource_limits` |
| `.env` | 新增 4 个配置项（默认留空 = 不设限） |

环境变量：`MUTEKI_WORKER_MEMORY` / `MUTEKI_WORKER_CPUS` / `MUTEKI_WORKER_PIDS_LIMIT` / `MUTEKI_WORKER_RESOURCES_REQUIRED`。

### 关键取舍

**不套用上游 full 的 2g/2cpu。** 那是他人的默认 sizing；Ghidra/Sage 常需更多。一个错的上限会表现为「题目解不出」，**比无上限更有害**。未配置时保持 unlimited，并在事件与摘要中**显式写明"unlimited"**，使「无上限」与「有上限」可区分。

**非法配置不静默丢弃。** 落进 `warnings` 并出现在摘要/事件中；`MUTEKI_WORKER_RESOURCES_REQUIRED=1` 时改为启动即报错。这正是 D07 要防的失败模式。

### 测试中发现并修掉的缺陷

首版 `describe_limits()` 在 `limits.unlimited` 时提前 return，**丢掉了 warnings** —— 即"配了限额但非法"会显示成干净的"无限制"，恰好是 D07 要防的静默丢弃。测试捕获后已修：warnings 现在无论是否设置都出现。

## 2. D04 — 启动失败分类与连续失败治理 ✅

### 为什么不直接回移上游

复核文档建议"参考固定上游实现适配"。核查后确认**不能直接复制**：

| 上游依赖 | 本地状态 |
|---|---|
| `muteki/swarm/coordinator_state.py` | **缺失** |
| `runtime_terminal_failure` | **0 处引用** |
| `_runtime_failure_code` / `_runtime_failure_phase` | **0 处引用** |
| `cli_launch_check.py` | 存在（批次 0 已回移） |

直接复制会 AttributeError。本轮**复现其语义**，适配本地实际结构。

### 本地已有的基础设施（复用，未重造）

- `cli_solver.py:1073/1836/1872` 已维护 `_runtime_process_started`（真实进程启动凭据）
- `coordinator_race.py:1229-1234` 已有 `prestart` 判定：`not process_started and not crossed_boundary`
- `cli_launch_check.launch_failure_code()` 已含 `worker_spawn_rejected` 等码
- `coordinator_dispatch.py` 的 `_report("worker_spawn_rejected", ...)` 是四个拒绝原因的统一通道

所以缺的只是**跨 worker 的连续失败计数**，改动面比预期小。

### 改动

| 文件 | 内容 |
|---|---|
| `muteki/swarm/dispatch_failure_governor.py` | **新增**。`FailureGovernor` / `is_prestart_rejection()` / `worker_is_prestart()` / `resolve_failure_limit()` |
| `muteki/swarm/coordinator_dispatch.py` | 新增 `_note_worker_dispatch_failure()`；`_report` 接入 |
| `muteki/swarm/swarm.py` | 初始化 `_dispatch_failure_governor` / `_dispatch_failure_limit_reached` |

### 关键取舍

**只有 pre-start 拒绝计数。** 运行期失败（模型超时、目标不可达、工具崩溃）属于既有 fruitless-interrupt / 反思路径，混入会因错误原因终止本可解的运行。

**只有真实进程启动凭据才清零**，仅创建 task 不清零 —— 否则"启动即崩溃"的 worker 会在系统其实健康时持续累加计数。

**阈值 5 是上游来源值，不是本地验证值。** 通过 `MUTEKI_MAX_CONSECUTIVE_WORKER_FAILURES` 覆盖（变量名以 `dispatch_failure_governor.ENV_MAX_FAILURES` 为准；本记录初稿写的 `MUTEKI_MAX_CONSECUTIVE_FAILURES` 缺 `WORKER`，按核查报告 5.2 于 2026-10-04 更正——用错名字会被静默忽略）；写错（如非数字）回退默认值而非静默关闭；显式设 `0` 才是关闭。另经核查 5.2：这批配置在批次 2 时并未接入 docker-compose，`.env` 改动到不了控制面进程——2026-10-04 批次已补齐 compose environment 透传。

**未叠加第二套空转计数器**，复用本地既有 fruitless interrupt（有测试断言源码中不出现第二套计数）。

**停止原因指明真实成因**，不是裸计数：

```
3 consecutive Worker dispatches failed before process start (engine=zcode): requested profile is unavailable
```
