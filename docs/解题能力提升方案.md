# 不换模型前提下的解题能力提升方案

日期：2026-09-29 · 基准：B 线（18200 Bonsai-27B）+ dsh 引擎 · 框架：muteki-local

## 0. 依据：B 线缺陷画像（全部来自实测）

| # | 缺陷 | 实测证据 |
|---|---|---|
| D1 | 多步推理断裂：注入失败后不反推隐藏过滤器 | run-18653：`' OR 1=1--` 被空格截断成 `'` 两次，无反思；做过 1 次回显提取却不对比 |
| D2 | 不主动用知识库 | C 线 8 worker 0 次 KB 读取；prompt 提示被 planner 稀释到不了 worker |
| D3 | 早停空转 | run-18652：26 次调用后 collect_idle 静默到 30 分钟超时，浪费 85% 预算 |
| D4 | planner 弱（同模型） | 只派发 `Solve no-pass-needed [web]` 一个 intent，无任务分解 |
| D5 | 提示稀释 | operator prompt 只到 planner，worker 只看 intent |

对应的两条已验证的正面事实：
- AGENTS.md 指引能拉动方向（引号注入 0→19、调用 26→155）——**"放到眼前"有效**；
- worker 会稳定使用 blackboard.py 这类 **CLI 工具**（三线全用了）——**"工具形态"比"文档形态"门槛低**。

## 1. P0：纯编排/提示改造（不动模型权重，当天可落地）

### 1.1 collect_idle 反思 worker（治 D3、D1）
位置：`muteki/swarm/coordinator_loop.py` 的 collect_idle 分支。
现状：worker 无新产出 → coordinator 空转等墙钟。
改造：连续 N=1 个 worker 无新事实/flag 时，由 coordinator 侧经 SharedGraph 写入一条
directive（机制现成：worker 经 `blackboard.py read-directives` 读取，coordinator_loop
已有 directive 生成/重-bootstrap 通路），强制下一个 worker：
1. 先读上一 worker 的**最后 5 条命令与结果**（黑板 facts 已有沉淀，需补命令级摘要）；
2. 按固定模板输出三种结构化行（复用 VERIFIED_FACT 的解析机制）：
   - `TRIED=<已排除的路径>`
   - `OBSERVED=<关键响应差异>`
   - `NEXT_HYPOTHESIS=<单一下一步假设>`
预期：把 D1 的"对比实验"变成填空题。27B 填空能力强于自由推理。

### 1.2 症状→行动卡（治 D2、D1）
位置：`worker_skills.py` 的 `_KB_POINTER`（AGENTS.md 指引，已验证能拉动方向）。
改造：从"分类路由"升级为"症状触发"——把高频死循环症状写成强制分支：
- 登录类：≥5 次凭据失败 → 停止猜测，执行 web-sqli.md 的 4 步过滤反推协议；
- 任何注入连续 3 次"语法错误/无变化"响应 → 停止换 payload，先做输入输出差异表；
- 目录扫描无果 → 检查响应头/报错页指纹（`security-misconfiguration.md`）。
每张卡必须包含**可直接复制的命令模板**（Bonsai 会执行命令，不擅长发明命令）。

### 1.3 FAILED_PROBE 结构化输出（治 D1）
位置：`cli_solver.py` 的 `_EXEC_PROMPT`（已有 VERIFIED_FACT=/DEADEND= 行级协议，黑板
解析器直接可复用）。worker prompt 增加一条：
`每次探测失败后，输出一行 FAILED_PROBE=<发送内容>|<收到关键差异>`。
黑板已有 fact 去重与 deadend 通道，coordinator 把连续 FAILED_PROBE 折叠进下一个
worker 的上下文——形成跨 worker 的失败记忆。

## 2. P1：知识形态升级（1-2 天）

### 2.1 KB 工具化（治 D2）
框架原生钩子已存在：`cli_solver.py` 的 `MUTEKI_KB_MCP_NAME`（`_KB_PROMPT` 教模型
"先查 KB 再动手"，当前为空未启用）。
改造：写一个零依赖 KB 搜索 CLI（sqlite FTS5 索引 24 域 + kali-claw 的 payloads.md），
以脚本工具形态提供（与 blackboard.py 同模式——三线都证明 worker 会调 CLI 工具），
注册为 KB MCP 或直接投影到 worker PATH。
预期：把"想到去 cat 文档"（27B 做不到）降级为"响应式查一条 FTS"（能做到）。

### 2.2 二次蒸馏：payloads.md 与 guides/（治 D1 弹药不足）
现状：24 域只蒸馏了每个域的 SKILL.md 主文件；kali-claw 每域还有 `payloads.md`
（web-sqli 含 10 类注入的全套 payload）和 `guides/` 深度指南未入库。
改造：扩展 `external/distill_kali_claw.py`，按域追加 payload 速查文件（体积可控，
按需 Read/MCP 查询）。重点域：web-sqli（编码/无空格变体表）、command-injection、
file-inclusion。

### 2.3 攻击类别覆盖度下限（治 D3、D4）
在 `_EXEC_PROMPT` 加一条交付前检查（Bonsai 可执行清单式指令）：
`提交 conclude 前，确认以下类别各至少尝试 1 次并在黑板上记录结果：
[注入(引号/注释/无空格变体) / 认证逻辑(默认口令/重置/越权) / 信息泄露(源码/备份/报错)]`
配合 1.1 的反思 worker，消除"单方向早停"。

## 3. P2：小模型协同时分复用（需实测显存）

主力解题模型不变（Bonsai 27B）。加一个**小模型常驻**承担 planner/反思器：
- 显存预算：Bonsai KVMem ~8.9GiB + 4B Q4 ~3GiB + 双 KV ≈ 13-14GB，2080 16GB
  理论可容纳，需实测确认（两条 llama-server 同机不同端口）。
- 分工：4B 只做三类低创作度任务（均已证明规则化任务小模型可用）：
  1. intent 再分解（读黑板 facts/deadends → 产出 ≤4 个方向）；
  2. FAILED_PROBE 归纳（把 N 条失败折叠成一条"已知排除+差异"）；
  3. conclude 前覆盖度审查。
- 收益：D4 直接消除（planner 不再是 27B 自己），D3 的反思质量提升。
- 注意：planner 上下文要走同一 KVMem 前缀缓存（system 固定）。

## 4. P3：长期选项（当前不建议）

- QLoRA SFT：用 NYU 官方 test_solver 的解题轨迹（剥离 flag）做轻量微调。
  2080 16GB 上 27B QLoRA 勉强可行但工程量大、有过拟合评测集风险；且"不换模型"
  精神下应先用尽 P0-P2。仅当 P0-P2 后解题率仍停滞时考虑。

## 5. 验证方法（回归基准）

- 回归题：no-pass-needed（人工 3 条命令基准 + writeup 链条）、poem（B 线能解的
  正对照）、gatekeeping（难对照）。
- 过程指标（比解题率更灵敏）：引号注入次数、回显对比次数、KB/工具查询次数、
  首个"换方向"事件时间、collect_idle 空转时长。
- 判定：P0 落地后 no-pass 仍未解但出现"对比实验"行为 → 方向正确，继续 P1；
  出现嵌套 payload 或解出 → 显著提升。

## 6. 优先级总览

| 优先级 | 项 | 改动量 | 预期收益 |
|---|---|---|---|
| P0 | 1.1 反思 worker + 1.2 症状卡 + 1.3 FAILED_PROBE | 编排/prompt 层，~1 天 | 消除早停与"失败即盲换" |
| P1 | 2.1 KB 工具化 + 2.2 二次蒸馏 + 2.3 覆盖度下限 | 新增 1 个 CLI 工具 + 蒸馏脚本扩展 | 查询门槛降到工具级 |
| P2 | 小模型 planner/反思器时分 | 显存实测 + 接线 | 根治同模型规划弱 |
| P3 | QLoRA | 大 | 最后手段 |
