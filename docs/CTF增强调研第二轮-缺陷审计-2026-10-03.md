# CTF 能力增强调研（第二轮）与本地版缺陷审计

日期：2026-10-03（Asia/Shanghai）。对象：`D:\AI\muteki-local`（v0.3.2 + 本地改造，完全离线 / 本地模型）。

本轮定位与前两份文档的关系：前序《CTF能力增强仓库调研》已覆盖 4 个仓库的**知识价值**判断，《上游同步评估》已覆盖 v0.4.0 的**回移台账**。本轮不重复这两部分，只做两件新增的事：

1. **把知识价值结论落到"本地实际缺什么"**——对照本地已落地的 KB / 检索 / 工具，给出增量缺口。
2. **把"版本落后"从文件计数升级为代码级实证缺陷**——逐项验证是否真的会影响本地 CTF 解题。

**本轮只做只读核查。未修改任何源码、配置、依赖或部署；未启动容器、未调用本地模型、未跑 CTF 题目。**

### 关于"本地模型能力有限"的判断

四个仓库里**没有任何一个能提升模型权重本身**。它们提供的是：知识（ctf-skills）、流程（reverse-skill）、工具封装（Anthropic 库脚本）。

真正有效的路径只有两类，本轮核查后优先级明确：

- **把确定性操作从"模型生成"转为"程序执行"** —— 本地已做（`ctf_tools.py` 的 http/decode/doctor，35 项工具 0 MISSING），这是**当前最高性价比的资产**。
- **上下文与停滞治理** —— 本地仍有真实缺口，见第 2 节 P1-②。

`KaliClaw v0.3.5` 的"139 技能覆盖"只验证了文档完整性与 bash 语法，**不证明端到端解题能力**；其旧版 CyberGym 报告 1087 实例仅 1 PASS 且中途失败。不能作为能力证明。

## 2. 本地版相对原版的待修问题（代码级实证）

版本落差：`muteki-local` = **0.3.2**；本地上游 `D:\AI\muteki` = **v0.4.0 + 5 个提交**（`git describe` → `v0.4.0-5-gd02d9e9`）。

> 修正前序文档一处结论：前文按 v0.4.0 评估，实际本地 HEAD **领先 v0.4.0 tag 5 个提交**（含 desktop chat 修复、pentest runtime 同步）。因此实际落差是 `0.3.2 → v0.4.0+5`，缺口比前文估计的略大。

`v0.3.2` tag 在本机浅历史中不存在，**无法建立精确三方合并基线**。以下结论均为内容级实证，不依赖该基线。

### P0-①　未知模型被套用通用美元价（**已闭环证实，直接影响预算判定**）

`muteki-local/muteki/core/cost.py:109`

```python
def price_for(self, model: str) -> ModelPrice:
    found = self.prices.get(model)
    if found is None and ":" in model:
        found = self.prices.get(model.split(":", 1)[0])
    return found if found is not None else _DEFAULT_PRICE   # ← 兜底估价
```

`_DEFAULT_PRICE = ModelPrice(input_per_m=1.0, output_per_m=3.0)`（`cost.py:59`），而 `PRICES` 表只有 `deepseek-v4-pro` / `deepseek-v4-flash` / `codex` 等云端条目。

**实际运行配置的模型是 `qwen3.8-27b`**（`data/sessions/_worker_config.json`），**不在表中** → 落入兜底。

以已记录的 run-20670 用量（input 6.31M / output 185K）折算：

| 口径 | 金额 |
|---|---|
| 本地版虚估 | **$6.86** |
| 本地推理真实现金成本 | **$0.00**（无 API 账单） |

上游已修：`cost.py` 头部注释为 `an unknown model remains unpriced instead of receiving a fallback`，并新增 `unpriced_calls` 计数（`usage.py` 541 行承载该语义）。

**影响链**：`coordinator_loop.py` 的 `_budget_exhausted()` 依赖 cost ledger。虚估会让本地模型在**没有任何真实花费**的情况下被判超预算；反之若调高美元预算以规避，又会失去一个有效的墙钟兜底。这是**当前唯一一个"账面数字直接误导决策"的缺陷**。

**建议**：随 `usage.py` 一起回移"未定价"语义，而非只把 `_DEFAULT_PRICE` 改成 0——改成 0 会让预算门控彻底失去约束。UI 侧改为展示墙钟/token/缓存口径。

### P0-②　Worker 容器无 CPU/内存/PID 上限（**已闭环证实**）

`container_exec.py:724-729` 是**条件式**追加：

```python
if memory:      run_cmd += ["--memory", str(memory)]
if cpus:        run_cmd += ["--cpus", str(cpus)]
if pids_limit and int(pids_limit) > 0: run_cmd += ["--pids-limit", str(int(pids_limit))]
```

而 `drivers.py` 中**没有任何** `memory=` / `cpus=` / `pids_limit=` 传入点，本地 `.env` 的 10 个键里也**完全没有**资源类配置：

```
MUTEKI_DEEPSEEK_API_KEY / MUTEKI_DEEPSEEK_BASE_URL / MUTEKI_FRUITLESS_INTERRUPT
MUTEKI_HOST_DATA_ROOT / MUTEKI_RUN_CONTAINER_PREFIX / MUTEKI_STANDBY_TIMEOUT
MUTEKI_UI_PORT / MUTEKI_WEB_PASSWORD / MUTEKI_WORKER_IMAGE / MUTEKI_WORKER_NETWORK
```

→ **实际以无资源上限运行**。

对本机（RTX 2080 16GB + Tesla T10 16GB，模型与容器共享内存/CPU）这是真实风险：反编译、`binwalk -e`、PCAP 大流量处理可能 OOM 或抢占推理资源，表现为**模型输出变慢/超时**，容易被误判为"题目太难"或"模型不行"。

上游 `worker_resource_limits.py`（230 行）提供了 `slim`/`full` 两档（`pids_limit=512`/`256` 等）与 `validate_pids_limit` 校验。

**注意**：上游 `full` 默认 2GB/2CPU 是**其**默认值，不能直接套用——Ghidra/Sage 很可能不够。需按本机实测设定。

### P1-③　上下文预算与长文件交付缺失

上游有、本地完全没有：`core/prompt_assembly.py`(311 行) + `solver/context_manifest.py`(97 行)。

本地已完成的部分（v0.3.2 回移时已移除 600/1000 字符截断）只解决了"文本被砍断"，**没有解决"文本完整但过长"**。而 run-20670 的失败画像恰恰是上下文压力问题（input 6.31M tokens / 88 次工具调用）——模型知道套路却不换方向。

这也是 D02 的技术前提：没有 manifest 就无法回答"这次实际送达了哪些章节、长度多少、哪些可选内容被省略"。

### P1-④　引擎适配层重构（**本轮判定：不要回移**）

上游把 `cli_driver.py` 拆成 `cli_engines/` 下的 21 个文件（adapter / argv / bins / process / health / registry / engines/*）。

本地只需 dsh + zcode 两个引擎，且**必须保留**上游已删除的 dsh/zcode 支持。迁移 21 个文件会引入 claude/codex/cursor 等无用路径和 `devin` 等新引擎，重构收益远低于风险。**明确建议不同步。**

### P2-⑤　Coordinator 已拆分为 11 个模块（**不同步**）

上游 `swarm/coordinator_*.py` 拆成 bootstrap/completion/control*/events/finalize/pentest_review/progress/reason/recovery/scheduler/schedule_dispatch。本地是 `coordinator_loop.py`(2881 行) 单体 + `coordinator_race.py`(2198 行)——正是前序 D02/D03/D04 想要改的地方，但**改法应是按需增能力，不是先做结构拆分**。拆分属跨层迁移（黑板 API + DB + 调度 + Worker + UI），风险高、收益不确定。

### 停滞治理：本地已优于上游，**无需回移**

值得记录的一点：本地 `coordinator_loop.py:1448-1521` 已有 barren backpressure pause（连续无产出的 worker 计数与终止），`MUTEKI_FRUITLESS_INTERRUPT=1` 已在 `.env` 生效。上游 `swarm/*.py` 中**未搜到** `consecutive_start_fail` / `no_new_evidence` 对应实现。

即前序 D04 中"上游连续启动失败计数"这一项，**上游 main 现状并不提供可直接回移的成熟实现**。D04 仍需本地自行设计（重点应放在 P0-① 的错误分类上：进程未启动 / 运行中失败 / 无新证据三者分开）。

## 3. 建议的落地顺序

```
第 1 步  P0-① 未定价语义   ── 纯记账语义，不改解题行为，零风险
第 2 步  P0-② 资源上限     ── 先测 Ghidra/Sage 真实峰值再定值
第 3 步  P1-③ 上下文 manifest ── 前置依赖，产出"实际送达了什么"的可观测性
第 4 步  D09-B/Crypto 子包  ── 此时才有上下文计量基础来证明是否有效
第 5 步  D10 真实模型对照   ── 冻结上述改动后建立基线
```

**先修记账与资源，再动上下文，最后才谈知识包**。理由：P0 两项是"数字骗人"和"资源互抢"，它们会**污染任何后续 A/B 评测的结论**——在虚估成本下比较解题率没有意义。
