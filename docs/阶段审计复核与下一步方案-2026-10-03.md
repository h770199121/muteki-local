## 3. 已确认问题，按实施优先级排列

### A01 — High：评测 token 重复累计，污染了失败归因和基线

位置：[run_challenge.py](../labs/nyu-ctf/run_challenge.py) 第 241–245、334–341 行；账本来源为 [cost.py](../muteki/core/cost.py)；前端也明确将 `cost.update` 作为累计值处理，见 [events.ts](../apps/web/ui/lib/events.ts) 第 2352 行起。

两个评测分支都直接 `sum(input_tokens/output_tokens)`。事件同时包含单 solver 的累计快照和覆盖这些 solver 的 challenge 累计快照，因此既重复计算同一 solver 的前后快照，又重复计算不同层级。

本轮重放 [run-20670.jsonl](../data/sessions/run-20670.jsonl) 的 8 条 `cost.update`：

| 口径 | input | output | 含义 |
|---|---:|---:|---|
| 将所有累计事件直接相加 | 6,312,289 | 185,575 | 恰好等于历史 `results.jsonl` 第 53 行及审计文档引用值；算法错误 |
| 每个 solver 只取最后一次累计值 | 1,563,948 | 52,737 | 已有 solver 账本覆盖量；不包含所有仅以 challenge scope 上报的调用 |

第二行也不能直接宣布为服务端精确总量：存在 challenge-only 调用，且 CLI 还有缺失 telemetry 时的估算路径。必须明确覆盖范围、估算标记与缺失项。

**修复方案：** 两个评测分支共用一个账本归约入口；使用稳定事件身份去重，明确累计快照与增量语义，按运行/执行代次/attempt 处理重放和恢复。优先读取最终权威用量记录；历史事件不能无歧义重建时输出“不完整”，不能把 solver 与 challenge 相加。旧结果原样保留，另产出带统计版本的更正结果。

**验收：** 同一累计事件重复出现不增加用量；solver/challenge 混合不双算；乱序、重放、恢复、缺失 telemetry 分别有结果；重放 run-20670 不再输出 6,312,289/185,575 为总量。

### A02 — High：评测成功判据绕开了真实执行来源

位置：[run_challenge.py](../labs/nyu-ctf/run_challenge.py) 第 241、335 行：`flag_found = ch["flag"] in json.dumps(events)`。

只要已知 Flag 字符串出现在任意事件中，脚本就判为 solved。题意、人工 hint、模型猜测或其他未验证文本均可触发。本轮用只包含 `text.delta` 的合成事件复现：没有工具执行，也没有 Flag 接受事件，现有表达式仍返回 True。

这不意味着产品 [Flag gate](../muteki/solver/gate.py) 本身失效；问题在评测脚本没有遵守同一结果契约。run-20670 本身仍是未解出，本轮没有把它改判成功。

**修复方案：** 正式结果以可信终态/接受记录为入口，并能回查真实 tool output 或产物来源；已知答案只由 evaluator 对比，不作为 Worker 输入。题目描述、hint、普通 text、被拒候选均不能直接判 solved。分别记录“找到候选”“gate 接受”“外部判题结果”。

**验收：** 普通文本或 hint 含答案仍失败；真实来源但 gate 拒绝仍不算接受；来源、接受记录和当前 attempt 对应时才成功；多 Flag 按不同 Flag 和题目要求计数。

### A03 — High：hint 例外同时绕过 URL 凭据封存

位置：[control_adapter.py](../apps/web/control_adapter.py) 第 251–253、306–313、350–355 行。

`free_text_keys` 分支直接保留整个字符串，跳过 `_redact_value()`，不只跳过文档所述的内容关键词启发式。于是 `text/hint` 内的 `http://user:password@host/` 也不封存，并可进入 `safe_hitl_echo()` 明文回显。这与既有变更记录中“URL userinfo 仍保留封密”的承诺不符。

本轮在内存中执行原函数体，使用虚构凭据与内存 SecretStore：URL 位于 hint 时未创建 secret 引用；同一个 URL 不启用 free-text 例外时会封存。结构化密码字段、显式 `secret://` 引用和强制封存 answer 的路径仍正常。这是函数级复现，尚未运行 Web 集成测试。

**修复方案：** 将“普通提示中提到 password 等概念”与“明确凭据载体”分开。允许普通 hint 通过，但保留 URL userinfo、显式 secret 引用、结构化凭据和 answer 的契约；确认秘密输入沿现有安全交付链处理，dsh 不支持时明确返回可理解的错误，不能退回明文日志。必要时使用已有结构化秘密输入入口。

**验收：** 同一回归集同时覆盖普通提示、带 userinfo 的 URL、结构化密钥、秘密引用、answer、日志回显与重试；不能只复跑此前未覆盖该分支的 19 项测试就关闭问题。

### A04 — High：Worker 计量可能使用错误模型，且未知模型仍套美元单价

位置：[cli_solver.py](../muteki/solver/cli_solver.py) 第 6900、6923–6940 行；[cli_driver.py](../muteki/solver/cli_driver.py) 第 2705–2708 行；[cost.py](../muteki/core/cost.py) 第 59、105–109 行。

有两个不同缺陷：

1. `_stream_cost()` 查询 `self.model`、`self.profile` 和父进程环境变量；正常模型配置在 `self.driver.profile`，构造器没有设置前两项。Worker 专属环境也不等于父进程环境。Profile 指定 Qwen、父进程没有模型变量时，内存执行原方法体实际选择 `deepseek-v4-flash`。run-20670 的部分价格也符合这一费率，但完整运行归因仍需集成复验。
2. 即使传入正确的 `qwen3.8-27b`，`price_for()` 仍返回通用单价。当前函数体在 1,000,000 input + 100,000 output 的夹具中计为 $1.30。

因此只回移 `price_for()` 的 unknown 分支仍不能解决当前 Worker 身份问题。

**修复方案：** 执行、健康检查、事件和计量共用解析后的模型身份。区分明确零 API 费用、未定价、精确单价及缺失/估算 telemetry；本地 API 费用不等于电费或硬件费用。USD 显示、预算准入、持久化、Protocol 2 settlement 与恢复必须使用同一语义。借鉴上游契约，不直接把新版 `usage.py` 拼进旧数据流。

**验收：** dsh profile 模型与记账模型一致；未知模型不冒充付费或零价；显式零价保持 token 统计；重复/恢复不重计；USD、墙钟和 Worker 数预算相互独立。

### A05 — Medium：资源参数未接入正常调度和 standby

位置：[coordinator_race.py](../muteki/swarm/coordinator_race.py) 第 1784、1807 行附近；[drivers.py](../apps/web/drivers.py) 第 1595 行起；[container_exec.py](../muteki/solver/container_exec.py) 第 498–502、724–729 行。

底层支持 memory/cpus/pids_limit，但正常 Coordinator 和 standby 创建容器时均没有传入。可确认的是“项目没有为这些路径配置显式上限”；Docker 当前不可用，不能据此声称本机虚拟机或守护进程绝无任何上限，也没有证据证明既往已经发生 OOM。

**修复方案：** D07 先统一有效配置及其验证、健康展示、事件记录和两个启动入口，再在用户确定的限额下实测。区分 OOM、PID、超时和磁盘错误。Ghidra/Sage/PCAP 的测量用于容量建议，不能自动生成硬阈值；不直接使用上游 full 的 2GB/2CPU 默认。

### A06 — Medium：离线契约和技能版本交付尚未闭环

位置：[llm.py](../muteki/core/llm.py) 第 30 行；[drivers.py](../apps/web/drivers.py) 第 500–516、1491–1504 行；[docker-compose.yml](../docker-compose.yml) 第 75 行；[worker_skills.py](../muteki/solver/worker_skills.py) 第 92–134 行。

模型端点当前已配置本地，但仍保留默认云端地址、无 profile 时的 claude 兜底以及 bridge 网络。源码没有建立“仅允许明确本地模型和靶场”的全链路契约。这里确认的是条件性缺口，不是已经发生云端请求。

技能投影遇到已有目录便直接返回其路径，复制异常可被忽略，缺少所用技能版本与复制失败的可靠反馈。源码 KB 更新不能证明已有或恢复中的 Worker 用到了新版本。

**修复方案：** D01 将允许端点与本地模式验证下沉到配置/启动边界；D06 记录技能内容指纹、投影结果与可见错误，保持运行中快照稳定，保留用户改过的文件。只生成候选检索结果不等于实际读到或使用知识。
