## 4. 本次确认的缺口

### 4.1 评测：修好单 Flag artifact 回查后，新引入多 Flag 时序回归

位置：[eval_verdict.py](../labs/nyu-ctf/eval_verdict.py) 376 行起。

当前代码以所有接受事件中最早的 seq 作为全部 Flag 的输出截止点。两个 Flag 分别产生、分别接受时，第二枚 Flag 的正常输出会落在第一枚接受之后，从而被排除。

本次用相同输入比较 `a29916f` 与当前实现：

```text
seq 1：工具输出 Flag A
seq 2：接受 Flag A
seq 3：工具输出 Flag B
seq 4：接受 Flag B
seq 5：run.finished，solved=true，flags=[A, B]

a29916f：solved=true
aa346c8：solved=false，1 枚 Flag 被列为 unlinked
```

应按每枚 Flag 自己的接受事件和来源关联计算时序，而不是使用全局最早接受事件。此项是已复现的新回归。

同一模块还存在以下可复现边界问题：

| 夹具/样本 | 当前结果 | 下一步修复 |
|---|---|---|
| `attempt=2`，artifact 输出事件没有 generation，接受事件为第 2 代 | `solved=true, attempt_matched=true` | artifact 分支也必须传播代次不确定性；目前 `gen_uncertain` 只在 inline 分支更新 |
| 同上，但 Flag 来自 inline 输出 | `solved=true, attempt_matched=false` | 明确严格评测成功与历史不确定结果的消费契约；当前 harness 仍只按 `verdict.solved` 统计 |
| artifact_id=`../outside`，Flag 放在 arts 外的临时文件中 | 被读取并判为成功 | 验证引用 ID、解析真实路径并限定在当前运行的 arts 内，处理绝对路径和符号链接；本次反例仅用项目内自建临时文件 |
| `run-23529` 的真实 artifact 摘要 | evaluator 输出与文件字节 SHA-256 不同 | 对原始 bytes 计算摘要，再独立解码搜索；不要对 `read_text()` 规范化换行后的字符串冒充文件 hash |
| 新写入的 live 结果行 | 没有 verdict_version | live 两分支统一序列化 verdict 版本；目前只有 `to_dict()` / 重放嵌套结果带版本 |

### 4.2 普通 Web 自动清单：事件枚举与字符串契约不一致

[drivers.py](../apps/web/drivers.py) 1408 行调用 `ev.model_dump()`，其默认 Python 模式保留 `EventType` 枚举。[events.py](../muteki/core/events.py) 的 `EventType` 是 `str, Enum`，`Event` 没有配置 `use_enum_values`。

而 [writeup_evidence.py](../muteki/solver/writeup_evidence.py) 使用 `str(event_type)` 与 `"tool.start"`、`"tool.result"`、`"run.finished"` 比较。`str(EventType.TOOL_CALL_RESULT)` 实际是 `EventType.TOOL_CALL_RESULT`，匹配失败。

本次从真实源码提取 `EventType` 类，将同一组事件送入当前清单生成器：

| 输入形态 | HTTP 交互 | 是否提取到成功 Flag |
|---|---:|---|
| 含真实 EventType 枚举的字典 | 0 | 否 |
| 同一组事件经过 JSON 序列化/解析 | 1 | 是 |

因此通过原始 JSONL 构建清单的脚本/HTTP 接口可以正常工作，普通 Web 首次生成复盘的新增路径却可能写出空清单；文件随后存在，又会阻止这条路径重建。应在边界统一使用 JSON 模式，或统一事件类型归一化；并为已有空/过期清单建立可解释的刷新规则。

这是实际 Enum 定义与消费函数的复现。由于宿主没有 pydantic，本次未运行完整 `SessionStore → standby → Web` 集成路径，下一批必须补该路径验收。

`final_text=body` 修复已静态确认，但当前 `run-23529` 的 seq 152 仍是旧完成事件，没有附录。它不能验证新代码的界面效果。本次搜索 `run-235*.jsonl` 中的报告完成记录只发现这条旧样本，未找到新的带附录完成事件。

### 4.3 截图与 HTTP 关联：基本修正有效，协议覆盖不足

per-worker FIFO 修正能处理不同 Worker 的乱序返回，但新增 `fallback` 会保留已经被 worker 队列消费的请求。本次夹具中，一个已配对请求后再出现无对应 start 的 result，后者又被错误配给同一旧 URL。应采用一次性消费的统一请求身份，不能在两个队列中保留重复可用副本。

新增 `test_cross_worker_interleave_pairs_correctly` 使用 A/B 发请求、A/B 返回的顺序；本次用改动前的全局 FIFO 也得到正确结果。因此这条测试没有真正覆盖原始乱序缺陷。应补 B/A 返回、缺失 start、同 Worker 并发和跨 generation 的关联用例。

方法识别目前只覆盖部分 POST 写法，以下真实命令形式均被当前模块标为 `method=GET, replay=true`：

```text
curl -b cookie.txt http://a.test/private
curl --data-binary @form.txt http://a.test/login
curl -X PUT http://a.test/item
```

Cookie 依赖不等于可无会话重放，POST/PUT 也不能用一次 GET 替代。应记录原始 method、会话依赖和重放条件；不确定时保留原始响应并明确标注不支持重放。

增量写 manifest 已经改进了总超时下的证据保留，但以下事项仍待完成：

- npx 带查询串 URL 失败的根因未定位，错误仍截取 500 字符；保留完整退出诊断再决定修改参数传递、复用浏览器或更换实现。
- 外层总超时仍为 140s，单页最多两次 `timeout_s+40`；需统一总截止时间和子进程清理，并避免写入过程被终止留下损坏 JSON。
- “首页 + 成功页至少 2 张”是原验收条件，不能改成“任意 2/4 张即关键页覆盖”。`run-23529` 现有两张均标为 `http page`，尚不能证明成功页验收通过。
- 普通 Web 入口目前只准备清单，尚无自动宿主截图服务。应明确产品支持范围与触发方式，不把评测脚本覆盖面等同于普通 Web 覆盖面。

该契约意味着：

- 纯离线环境仍能启动界面和控制面、配置/调用可达的本地或局域网模型、处理本地文件与可达靶机、使用本地知识和已安装工具、生成报告/读取证据、恢复任务和管理资料。所需模型、依赖、静态资源及浏览器由本地安装或离线交付包提供。

- 网络可用性和降级行为由配置、启动、客户端及任务执行层实现，不靠提示词保证；不因支持纯离线而添加全局禁公网防火墙或靶机地址白名单。具体配置字段仍纳入现有配置校验入口。

### 6.2 D01：联网能力可用，纯离线功能正常

当前 `apps/web/drivers.py` 711 行的 `offline` 默认 False；设 True 又在 734 行强制 `worker_network=none`，会切断需要保留的模型 API/局域网通信。`muteki/core/llm.py` 仍有默认公网模型地址，standby 构造仍显式 `web_access=True`。这些开关不能完整表达“目标网络范围不限、辅助联网能力可用、核心功能离线可运行”，需要按职责拆分语义。

实施范围：

1. 在 [worker_config.py](../apps/web/worker_config.py)、[worker_profiles.py](../muteki/solver/worker_profiles.py) 和设置界面分别管理模型端点、目标地址、搜索/知识库/工具服务及下载/更新选项。模型 API 保持显式配置和本地/LAN 范围；靶机支持本地、LAN、公网地址，不增加目标 IP/CIDR/域名白名单。辅助服务按自身配置工作，不套用模型端点限制。
2. 在 [llm.py](../muteki/core/llm.py)、[drivers.py](../apps/web/drivers.py)、[profile_health.py](../muteki/solver/profile_health.py) 和各引擎启动入口保持模型选择一致，覆盖规划、标题、审查、主 Worker、继续、追问和报告。缺模型配置/模型不可用不隐式转云；某个搜索或更新服务不可达不等于模型 Profile 不健康。
3. 保留现有评测专用的工具隔离语义，另行实现产品的联网/离线兼容。Worker 网络保留控制面、模型 API 与靶机访问，不能为证明“离线支持”统一设为 `network=none`。通过实际请求结果或轻量、可超时的能力检查判断可用性，不把固定公网探测站点作为启动依赖；显式选择离线运行时跳过辅助公网调用，并保留本地/LAN 功能。
4. 公网搜索、公网知识库、工具服务、代理和浏览器联网路径在网络可用且配置允许时正常使用。按能力处理 DNS 错误、连接失败、超时和认证错误，保留准确原因；可选能力失败时切换本地资料/缓存或报告该能力不可用，已有任务状态与证据不丢失。只有必要模型或目标不可达等无法继续任务的条件，才进入相应失败/暂停流程。
5. 镜像、Python/Node 包、浏览器和工具运行时优先使用已安装内容；联网时允许下载缺失/新增组件并记录版本及摘要，离线时使用本地缓存或离线包。完整离线交付应自带核心功能依赖，不能把首次联网安装作为隐含前提；确有缺项时列出具体组件与离线补齐方式，不使其他已具备条件的功能失效。npx 路径按同一规则处理。
6. 自动外网更新在有网络时可使用，检查/下载不阻塞启动、求解或报告；平台自身的来源和安装时机遵循第 6.9 节已确认契约。离线或更新失败时继续运行已安装版本，保留本地/局域网更新入口；下载不完整不能覆盖已验证缓存，恢复网络后可重新检查和下载。

验收矩阵：

| 环境/路径 | 必须通过的行为 |
|---|---|
| 联网 | 本机/LAN/互联网靶机均能进入正常执行路径，无地址范围拦截；搜索、远程知识库、下载和自动更新按配置工作 |
| 纯离线且核心依赖已备齐 | Web/TUI 启动、静态资源、可达本地/LAN 模型、本地文件/靶机、知识检索、已装工具、截图、报告、证据读取、自动恢复与手动资料管理可运行 |
| 可选公网服务不可用 | 明确降级或使用已有缓存；更新检查和外部搜索失败不阻断启动或使任务被误判为模型失败 |
| 公网目标在断网时不可达 | 明确报告目标不可达，保留运行资料；不假装能够离线访问该目标，不将其与本地功能故障混为一谈 |
| 运行中断网/恢复 | 已生成证据和状态不丢失，恢复任务幂等；联网能力重新可用后可恢复使用，失败暂停仍遵守 D05 |
| 缺依赖或更新中断 | 离线缺项可解释，有离线补齐路径；联网下载/更新失败不破坏现有可运行版本 |

使用受控服务模拟联网、断网、DNS/超时和下载中断，检查各能力独立退化，避免用全局联网探测代替实际功能验收。正式离线评测的输入/工具隔离口径继续独立维护，D10 仍不在本轮新增计划内。

### 6.5 D04/D05：启动失败治理、停滞和恢复

在现有 `dispatch_failure_governor`、Coordinator 主循环、`RunManager.resolve()` 和 6D 对账路径上收尾：

- D04 保留当前配置来源的连续启动失败上限 5；补成功启动清零、运行中失败不混计、存在其他 Worker 时取消、故障注入开关退出后归零的验证。停滞判定优先依据重复动作/无新事实等可观测状态，不从历史 min/max 推导新超时阈值。
- D05 按用户选择实现**重启自动恢复，恢复失败时暂停并提示**。启动阶段先识别最新未闭合 generation 并持久化中断/恢复状态，核对旧执行者与控制权限，再通过现有完整 Coordinator 的续作路径自动进入下一 generation；不能仅自动启动一个 standby 来冒充恢复完整任务。
- 恢复准入必须幂等：同一待恢复 generation 只能提交一次恢复动作，持久化执行所有权和结果；并发启动、连续重启或迟到事件不能重复启动同一任务。人工已经暂停/停止/完成的任务不因服务重启而自动续跑。
- 恢复时复用 D01 配置、D02 原文来源和 D08 账本；端点/模型不可用、旧运行所有权未释放、必要文件或资源条件不满足时，转为可持久化的暂停状态并提示具体原因。后续重启不绕过该暂停，用户处理原因后可用既有手动继续入口重新发起，不自动无限重试。
- 恢复判断区分必要条件与可选联网能力：搜索、公网知识库或更新服务不可用不应单独阻止自动恢复；任务必须访问的目标不可达时才暂停并说明目标/网络原因。
- 自动/手动恢复均接续同一任务的已消耗用量和剩余预算；服务停机、恢复失败后的等待按第 6.7 节不扣任务时间额度。多次重启不能重复扣时，也不能借新 generation 重新获得完整预算。
- 补内存/磁盘/SSE 一致性、无 winner 恢复、长 hint、旧执行者和迟到事件隔离；保留单次恢复结果和所用配置版本，故障信息不得夹带凭据。

验收：中断后自动恢复成功；连续两次重启没有重复 Worker 或预算重置；恢复失败后保持暂停且提示可见，等待不扣时间额度；人工暂停/停止任务不自动恢复；缺 winner、失效端点、旧 Worker 未退出、取消和手动继续夹具通过。现有实现只完成部分中断对账，自动恢复是本轮已确认的待实施行为。

### 6.7 D07/D08：资源、保留策略与运行账本

资源配置沿用 [worker_resources.py](../muteki/solver/worker_resources.py)、Compose 和各 Worker 启动路径；保留/清理由 [RunManager.retention_sweep](../apps/web/run_manager.py) 统一处理，账本沿用 [cost.py](../muteki/core/cost.py) 和已有运行 settlement。

- D07 按用户选择先测量：覆盖模型驻留与 Worker 同时运行、Web 通用工具、截图和恢复阶段的 CPU/内存/PID、输出和磁盘增长；列出测量条件、峰值、失败及并发关系，再提出各项上限的建议，由用户确认后写入配置。不能仅用观测 min/max 直接生成硬阈值。现有 512m 只是当前配置，不自动推广为推荐值。
- Coordinator、standby、resolve 使用同一份有效限额；非法配置、OOM、PID/磁盘/输出上限和墙钟结束各自给出准确原因，收尾释放进程/容器并保留允许保留的证据。
- 原文超限时记录截断/未落盘原因和可恢复指针；界面展示、日志、产物和运行目录使用同一份保留策略，避免删除仍被报告/证据链引用的内容。
- 按用户选择实现**默认保留、手动归档/清理和空间提示**。当前 `server.py` 默认开启 3 天归档、7 天删除，与新要求不同；实施时关闭默认自动归档/删除扫描，不以旧参数继续清理。空间提示优先显示当前用量、剩余空间和增长，不在未确认时新增报警阈值或自动删除策略。
- 手动清理先展示具体运行、目录、大小和仍被引用的证据范围，再由用户执行；保护活动/恢复中的运行和固定保留资料。默认保留不等于忽略写入失败：磁盘不足时保留可用状态、停止相关写入并明确提示，不偷偷删除历史文件腾空间。
- D08 将 Worker、Coordinator、standby 和重开 generation 的累计/增量用量分开归约，避免重放重复记账、跨层重复相加或恢复后预算无意重置；缺失遥测标记不完整。
- 任务时间额度按用户确认排除**服务停机及恢复失败后的等待时间**。持久化已扣时间、等待区间和恢复边界，恢复后接续剩余额度；另外记录首次启动后的自然历时，界面不能混用这两个指标。该选择不清零已有 token、工具用量或其他已发生消耗，也不把普通软暂停一律改成免计时。
- 校验预算在跨 generation、重复恢复事件和多次重启下保持一致；已耗尽的预算不能因恢复得到重置。无法从历史记录精确重建时明确标记缺口，不把未知消耗当作零。
- 本地推理继续区分“无外部 API 账单”和“资源消耗”；局域网 API 价格由显式配置和实际计量决定，不仅因私网地址就推断为免费，也不套用云模型默认单价。资源/墙钟预算独立于美元显示。

验收：限额从配置到实际运行可追溯，超限夹具原因正确且清理完成；pin/活动运行/仍被引用产物的保留行为符合已确认策略；使用可控时钟验证停机/恢复失败等待不扣时间、恢复沿用剩余预算、自然历时仍包含等待；重复事件和多 generation 账本一致；不得依据未核实价格触发错误停止。
